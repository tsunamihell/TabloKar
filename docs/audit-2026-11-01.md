# گزارش بررسی و اصلاح تابلوکار

تاریخ: ۲۰۲۶-۱۱-۰۱ — دامنه: نسخهٔ موجود در همین پوشه، بدون استقرار روی محیط عملیاتی.

## معماری و وضعیت واقعی

پروژه یک workspace مبتنی بر npm است. `client` از React، TypeScript، React Router، Vite و Tailwind استفاده می‌کند. درخواست‌های `/api` در محیط توسعه از پراکسی Vite به Express روی پورت ۵۰۰۰ می‌روند. سرور از Prisma و SQLite با چهار مدل Role، User، ShopSetting و ProductTypeCatalog استفاده می‌کند. رمزها bcrypt و نشست‌ها JWT در کوکی HttpOnly هستند. middleware هویت و نقش فعلی را از دیتابیس می‌خواند؛ تغییر نقش یا غیرفعال‌شدن حساب صرفاً به ادعای قدیمی داخل توکن وابسته نیست.

بخش‌های فعال: ورود، خروج از طریق پاک‌کردن کوکی، دریافت پروفایل کاربر، ویرایش تنظیمات توسط مدیر و نمایش کاتالوگ. سفارش‌ها، مشتریان، طراحی، تولید، نصب و صندوق در App به PlaceholderPage متصل‌اند و گردش کار واقعی ندارند. کاتالوگ فعلاً فقط خواندنی است؛ الزام ویرایش آن در `openspec/specs/shop-settings/spec.md` هنوز پیاده نشده است. API مدیریت کاربران هم وجود ندارد. این موارد توسعهٔ قابلیت هستند و با اصلاح باگ‌های هسته تکمیل نمی‌شوند.

## اشکالات اصلاح‌شده

| تشخیص اشتباه مسیر دیتابیس در BAT | Seed می‌توانست در هر اجرا دوباره اجرا شود | تشخیص مسیر حذف شد؛ Prisma از DATABASE_URL استفاده می‌کند، migration اجرا و Seed اکنون فقط رکوردهای مفقود را ایجاد می‌کند |
| Seed تنظیمات، قیمت، نقش و مجوزهای موجود را بازنویسی می‌کرد | از دست رفتن تغییرات کاربر | همهٔ updateهای Seed خالی شدند؛ آزمون اجرای دوباره، حفظ تنظیمات، قیمت و نقش را بررسی می‌کند |
| حساب جدید با رمز ثابت ساخته و رمز در خروجی ثبت می‌شد | دسترسی با رمز قابل پیش‌بینی | ساخت مدیر جدید به ADMIN_PASSWORD وابسته است؛ نصاب فقط با INSTALLER_PASSWORD ساخته می‌شود؛ ثبت رمز و دکمه‌های ورود سریع حذف شدند |

| خطای دیتابیس در احراز هویت، ۴۰۱ گزارش می‌شد | خروج ظاهری کاربر هنگام خرابی سرور | تفکیک خطای JWT از خطای زیرساخت و بررسی معتبر بودن ID توکن |
| CORS هر Origin را با credentials می‌پذیرفت | اعطای مجوز خواندن پاسخ به مبدأهای دلخواه | فقط مبدأهای صریح CORS_ORIGINS؛ پیش‌فرض بدون مجوز cross-origin |
| ورود و تنظیمات نوع داده را درست بررسی نمی‌کردند | تبدیل object یا null به رشته و ذخیرهٔ دادهٔ نامعتبر | اعتبارسنجی ورودی، محدودیت طول، رد ارز غیرتومان و تبدیل فیلد nullable به رشتهٔ خالی |
| خواندن تنظیمات از الگوی find سپس create استفاده می‌کرد | رقابت ساخت رکورد اولیه | upsert برای رکورد singleton |

| کلید ذخیره بیرون فرم مستقیماً handler را صدا می‌زد | دورزدن اعتبارسنجی HTML مانند required | اتصال دکمه به فرم با form و type=submit |
| صفحات تنظیمات و کاتالوگ خطای HTTP را موفق تلقی می‌کردند | فرم خالی یا کاتالوگ خالی بدون خطای واضح | بررسی res.ok و نمایش خطا |
| رابط کاربری حتی با شکست درخواست خروج کاربر را پاک می‌کرد | نمایش خروج درحالی‌که کوکی هنوز معتبر بود | پاک‌کردن state فقط پس از پاسخ موفق و اعلام شکست در UI |

## رخداد اجرای اولیهٔ آزمون

قبل از مشخص‌شدن اتصال آزمون‌های قدیمی به دیتابیس اصلی، یک بار `npm test` اجرا شد. همان آزمون‌ها نام، شهر، آدرس و تلفن تنظیمات را با دادهٔ آزمایشی نوشتند. مقدار قبلی در اختیار این بررسی نبود؛ بنابراین بازگردانی حدسی یا اجرای Seed برای پوشاندن این تغییر انجام نشد. اصلاح ایزوله‌سازی پس از کشف این مشکل انجام شد. برای بازیابی دقیق، نسخهٔ پشتیبان قبل از این اجرا یا مقادیر تأییدشدهٔ صاحب داده لازم است. این محدودیت بخشی از نتیجهٔ کار است.

## اعتبارسنجی

- مجموعهٔ قبلی: ۱۴ آزمون؛ مجموعهٔ توسعه‌یافته: ۲۶ آزمون سرور شامل ۱۲ مورد رگرسیون.
- `npm test`: آزمون‌های سرور و بررسی TypeScript کلاینت.
- `npm run build`: کامپایل سرور و ساخت production کلاینت.
- آزمون‌های رگرسیون شامل ورودی نامعتبر، JSON خراب، خطای دیتابیس ورود و احراز هویت، توکن فاقد ID معتبر، CORS، حفظ داده در برابر ورودی نامعتبر، nullableها و تکرار Seed هستند.
- ابزار مرورگر برای آزمون تعاملی فراخوانی شد، اما با خطای `The browser access host is unavailable` مواجه شد؛ آزمون بصری/تعاملی انجام‌شده ادعا نمی‌شود. آزمون کلاینت فعلی فقط type-check است.
- راه‌انداز BAT روی دیتابیس اصلی اجرا نشد، چون migration/seed می‌تواند آن را تغییر دهد؛ منطق Seed روی دیتابیس موقت آزموده شده است.
- تحلیل گراف همراه با بازخوانی مستقیم منبع انجام شد. گراف در migration SQL پوشش ناقص داشت؛ فایل SQL مستقیم خوانده شد. فایل env و محتوای دیتابیس وارد گراف نشدند.

## موارد باقی‌مانده و مرز آماده‌بودن

1. بازیابی مقادیر تنظیماتِ پیش از اجرای اولیه نیازمند شاهد معتبر است.
2. نشست JWT با خروج صرفاً از مرورگر پاک می‌شود؛ کپی توکن تا انقضا اعتبار دارد. ابطال مرکزی، مدیریت نشست و تغییر رمز به طراحی مدل نشست/کاربر نیاز دارند.
3. حساب‌های قدیمی ممکن است همچنان رمزهای اولیه داشته باشند. این اصلاح رمز حساب موجود را تغییر نمی‌دهد؛ ورود سریع حذف‌شده جایگزین تغییر رمز حساب قدیمی نیست.
4. محدودسازی تلاش ورود، ثبت رویدادهای احراز هویت، سیاست بازیابی رمز و آزمون مرورگری خودکار هنوز وجود ندارند.
5. مخفی‌کردن منوی نقش‌ها به‌تنهایی مجوز سرور نیست. فعلاً فقط ویرایش تنظیمات endpoint مدیریتی واقعی است؛ برای ماژول‌های آینده باید مجوز API مستقل پیاده شود.
6. خواندن تنظیمات و کاتالوگ در API عمومی باقی مانده است؛ برای اطلاعات غیرعمومی باید قرارداد دسترسی جداگانه تعریف شود.
7. استقرار production شامل ارائهٔ فایل‌های client، مسیر fallback برای SPA، HTTPS، پشتیبان‌گیری SQLite و بازیابی عملی هنوز در این نسخه بسته‌بندی نشده است. کوکی production از نوع Secure و نیازمند HTTPS است.
8. بررسی وابستگی‌ها از نظر advisoryهای آنلاین و ممیزی امنیتی جامع در این گزارش ادعا نمی‌شود.

هیچ commit یا انتشار خارجی انجام نشده است. فایل‌های اولیه از ابتدا در وضعیت untracked بودند و حفظ شدند.
